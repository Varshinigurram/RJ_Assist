**Experience**  
This week we examined binary search trees (BSTs) and the core operations that keep them useful. I learned the formal definition: every node’s left subtree holds smaller values and its right subtree holds larger values. The class covered how to insert a new value while preserving this rule, how to delete a node without breaking the ordering, and how to search by comparing keys and moving left or right. We also explored the three traversal orders— inorder (left‑node‑right), preorder (node‑left‑right) and postorder (left‑right‑node)—and noted that inorder produces a non‑decreasing sequence. The material emphasized that the tree’s shape directly influences the cost and correctness of each operation.

**Feelings**  
When I visualized the BST property, a sense of clarity washed over me; the left‑smaller/right‑larger rule felt intuitive after a few examples. However, deletion—especially handling nodes with two children—occasioned a moment of unease because I had to remember to replace the node with its inorder predecessor or successor. I was pleased, though, when I realized that inorder traversal could generate a sorted list automatically, which made the connection between data structure and algorithm feel concrete.

**Learning**  
My biggest insight was the tight coupling between structure and operations. A skewed tree can make search, insert, and delete degrade to linear time, while a balanced shape yields logarithmic performance. I also grasped why inorder traversal yields sorted order: because of the BST property, visiting left (smaller) then node then right (larger) naturally creates a non‑decreasing list. Preorder and postorder were linked to different practical needs—preorder for quick reconstruction and postorder for safely deleting children before parents. These relationships showed how a single data arrangement can support multiple algorithms.

**Application**  
Imagine I need a simple in‑memory map that stores employee IDs as keys and names as values, with fast look‑ups and the ability to list employees alphabetically. I could implement the map using a BST. Insert and delete operations would keep the tree ordered, and searching for an ID would follow the BST search path, typically O(log n) on average. To produce an alphabetical employee list, I would perform an inorder traversal, which naturally yields the IDs in ascending order. If I later wanted to serialize the map for backup, I could use a preorder traversal to capture the structure and later rebuild the tree.

**Conclusion**  
The week reinforced that BSTs are powerful because their ordering property underpins search, insertion, and deletion, while traversals unlock sorting, serialization, and safe cleanup. My next step is to code a BST class in my preferred language, experiment with edge‑case deletions, and test how inorder traversal automatically sorts the stored keys. This hands‑on practice will cement the theory and prepare me for more advanced balanced‑tree structures.
